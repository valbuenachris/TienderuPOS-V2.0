# POS v2 development rules

- This is a clean TypeScript/NestJS + React POS. Do not copy PHP/CodeIgniter implementation files here; `../pos-gres` remains the legacy reference until cutover.
- `tec_tenants` is the approved tenant registry (the only approved DDL): `id uuid, name, host, status ('active'|'inactive'), created_at`. The v0.3.11 tenant-management tables (`tec_subscription_plans`, `tec_tenant_subscriptions`, `tec_tenant_payments`, `tec_tenant_activity_logs`) are an approved DDL exception too; their only script is `docs/migrations/v0.3.11-tenant-management.sql` and the operator runs it before deploying (the API never runs DDL). Super admin is a shared `tec_groups` row `name='super_admin'` (`tenant_id IS NULL`) plus a `tec_users` row in the default tenant. `AdminGuard` accepts `admin` and `super_admin`; `SuperAdminGuard` protects global endpoints (`GET/POST /api/tenants`, `/api/tenant-management/*`, `POST /api/auth/switch-tenant`). **Every token carries `home_tenant_id`** (equals `tenant_id` on login; on `switch-tenant` it stays the home tenant while `tenant_id` is the target) and **`super: true` when the user's resolved group is `super_admin`**. The session payload mirrors `homeTenantId` and `super`, and `TenantContextGuard` rejects any mismatch; cross-tenant scope additionally requires `claims.super === true` AND the resolved group `super_admin`. `GET /api/auth/me` returns `super: boolean`. Audit stays in API logs for now. The web keeps a session-only `selectedTenantId`: a super admin login starts in **global view** (dropdown shows "Seleccionar tenant…", the sidebar header shows the generic "Tienderu POS · Manager" instead of any tenant settings, the sidebar lists only Dashboard global and Gestión de tenants —Tenants/Planes/Pagos/Datos—, and tenant-scoped routes including `/config` redirect to `/dashboard/global`; **v0.3.86** the sidebar logo in global view is the bundled platform asset (`web/src/assets/tienderu-logo.svg`, "P" fallback via `onError`), never `settings.logo_url` — the superadmin token still carries the home tenant (or the last switched one), so tenant branding must not render in global view (the asset is a **placeholder** to be replaced by Tienderu's real logo); picking a tenant runs `switch-tenant` and reveals the full POS menu — inside a selected tenant the sidebar keeps **that tenant's** logo/name on purpose (v0.3.86 decision); clearing the dropdown returns to global view. `/config` is tenant-scoped, never shown in global view. Non-super users are never gated and always see the POS menu.
- The Supabase schema is immutable. Do not add migrations, alter tables, create indexes, change policies/grants, or enable ORM schema synchronization. **Database triggers/rules on stock tables are forbidden**: the API owns all stock math inside transactions; an enabled trigger double-applies deductions/additions. Exception: the only allowlisted trigger is `trg_calculate_reward_points`; `DatabaseService` logs an error at startup if it finds any other enabled trigger on `tec_sales`, `tec_sale_items`, `tec_products`, `tec_purchases` or `tec_purchase_items`.
- Use the typed `SupabaseService` for simple table CRUD and types in `api/src/database/database.types.ts`; use `pg` for atomic multi-table sales, BYTEA session compatibility, and exact-text monetary reports. Type every SQL result from the known table row types or an explicit aggregate projection.
- Keep database/service-role credentials in the API `.env` only. React uses the Nest API and TanStack Query for server state; do not fetch server data with `useEffect` or connect the browser directly to Supabase.
- All tenant-owned SQL must use `tenant_id` from the verified JWT/tenant resolver. Never accept a tenant ID or database credential from browser input.
- Authentication and store scope use `tec_users` plus its tenant-matched `tec_groups` row; `group_name = 'admin'` can select tenant stores, while a cashier is limited to `tec_users.store_id`.
- POS staff authenticate from `public.tec_users`; customers are `public.tec_customers`. For sales, `created_by` is the POS employee, `customer_id` is the customer, and `user_id` stays unused/null. The POS customer picker searches server-side via `GET /api/catalog/customers?q=` (matches name/email/phone within the tenant/store, max 100 rows, UI debounces 300 ms and shows 10); "Cliente ocasional" sends no `customer_id`.
- Payment methods (`paid_by` in `tec_payments`) are restricted to `cash`, `CC`, `Transferencia`, `Sistecredito`, `ADI` and `credito` (legacy-compatible casing; `Sistecredito`/`ADI` are what the old POS writes). `due` records no payment and leaves `status = due`; cash can register a partial payment. The POS label "Crédito [tienda]" maps to the stable value `credito`; never store tenant/store names in `paid_by`.
- The POS confirms every sale in `SaleConfirmationModal` before calling `POST /api/sales`. Cash may send `amount_received` (and optional `change_amount`, which must equal `amount_received - total`); the server applies `paid = min(amount_received, grand_total)` so `tec_sales.paid` and `tec_payments.amount` never exceed the total, returns `change_amount`, and computes `status` itself. Never trust a client-sent `status`, and never persist change (the immutable schema has no column for it).
- Manual discounts: `discount_type` (`fixed`|`percent`) + `discount_value` (decimal string). Percent applies over `subtotal + tax` and must be ≤ 100; fixed must be ≥ 0 and ≤ the pre-discount total. Store the amount in `order_discount`, the raw value in `order_discount_id` (`"10%"` or the amount), `total_discount = order_discount`, `product_discount = 0`, and populate `product_tax`/`total_tax`/`order_tax`/`order_tax_id`/`rounding`. Sale `update` must reapply the stored discount (percent recalculated, fixed kept) so `grand_total` stays consistent.
- The POS ticket is rendered by `web/src/components/SaleTicket.tsx` and printed at 58 mm via the `.print-receipt` container (`@media print` hides everything else, `@page size: 58mm auto`). The QR is generated in the browser with the `qrcode` package from the sale payload; do not add a backend QR endpoint or send sale data to third parties. The same component is reused for the on-screen preview modal (`preview` prop), which also offers WhatsApp (formatted plain text, `customer_phone` from `create`/`detail`, +57 for 10-digit Colombian numbers, WhatsApp Web fallback) and PDF (`html2pdf.js`, 58 mm) actions. The actions render only with `preview` so the hidden print node stays clean (the PDF captures only the ticket node, not the buttons). The footer ends with a two-line branding block: `Facturado con Tienderu POS` + `email - teléfono` (from `settings.email`/`settings.phone`, falling back to `info@tienderu.com` · `3104039092`).
- IDs use existing identity/sequences; omit `id` on inserts and use `RETURNING id`. Primary keys are global; do not allocate `MAX(id)+1` per tenant.
- Tenant branding (v0.3.74): the per-tenant logo lives in `tec_tenant_settings.logo_url` (no new DDL; the `tec_tenants` registry stays untouched). Upload/delete remain in `POST/DELETE /api/settings/logo` (admin-only, Supabase Storage `productos/logos/<tenant>_<ts>.<ext>`, 2 MB, PNG/JPG/WEBP/SVG, previous file removed). `GET /customer/profile` now also returns `tenant: { id, name, logo_url }` (graceful fallback if the settings row/table is missing) so the mobile app caches the URL in SharedPreferences and shows it on the login screen and home AppBar (fallback to the default icon). The web sidebar renders `settings.logo_url` (max-height 40px, fallback letter "P").
- Per-tenant settings live in `public.tec_tenant_settings` (approved DDL, v0.3.16; script `docs/migrations/v0.3.16-tenant-settings.sql`): one row per tenant (`tenant_id` UNIQUE) with branding, fiscal/contact fields, currency/timezone/language, taxes and ticket fields. Never expose SMTP secrets. `SettingsService` detects the table at startup and **re-checks lazily every 30 s**, so it switches to per-tenant mode without an API restart once the migration is applied; when present it reads/writes **only the active tenant's row** (provisioning it with `site_name` = tenant name if missing) and the tenant bootstrap ensures the row too; when absent it falls back to the legacy global `tec_settings` (introspected columns, 30 s cache, first/shared row). `assertTenant` validates that the tenant exists (non-deleted) — it must not require POS users. `GET /api/settings` (full editable set + `supported`), `PUT /api/settings` and logo upload/delete are admin-only (`AdminGuard` accepts admin+super_admin); `GET /api/settings/pos` is authenticated and returns only the POS display subset (`POS_DISPLAY_COLUMNS`) that the session/ticket need. Logo uploads go to `SUPABASE_PRODUCT_BUCKET` under `logos/` and require `logo_url`.
- Tenant creation (`POST /api/tenants`, super-admin) is transactional bootstrap: inserts `tec_tenants`, a default store (`Tienda Principal`, code `MAIN`), a default admin user linked to the shared `admin` group (username `<slug>_admin` with `_1`, `_2`… on collision, checked globally, slug ≤20 chars; generated password hashed with `USER_PASSWORD_METHOD`/`BCRYPT_ROUNDS` via `api/src/common/password.ts`) **and** a subscription — a 14-day trial for free/default plans, or an active monthly subscription (start today, `subscription_end_date`/`next_billing_date` +1 month) when the chosen `plan_id` is paid (price > 0) — logging `tenant_created`. The plain password is returned **only once** in the creation response; never log or persist it. `PATCH /api/tenants/:id` (super-admin) updates `name`/`host`/`status`, allows clearing the host with `null`; `host` is informational and has **no uniqueness enforcement** (single-domain model, all tenants may share `pos.tienderu.com`). `DELETE /api/tenants/:id` (super-admin) is a **soft delete** (`status='deleted'`, `host=NULL`, 204), logs `tenant_deleted` and only proceeds when the tenant has no sales, no active non-admin users and no store inventory; the active tenant cannot delete itself. Admin/staff groups are shared (`tenant_id IS NULL`) so no per-tenant groups are created. Never resolve a store from `user.store_id` without checking it exists in the active tenant's `stores` list (super admin may carry a store from another tenant).
- Login is **credential-based** (single-domain SaaS): `AuthService.login` looks up the user by username/email across `tec_users` (case-insensitive, active only) and uses that row's `tenant_id`; the HTTP Host header is never used to pick a tenant. Ambiguous (>1 exact match) or unknown identities fail as invalid credentials (no tenant enumeration), and `inactive`/`deleted` tenants are rejected. `TENANT_HOST_MAP`/`DEFAULT_TENANT_ID` remain only as a fallback bucket for lockout attempts of unknown identities. Keep this behavior when touching `AuthService.login`.
- Tenant billing (v0.3.23, `api/src/billing/`): invoices are **derived** (no DDL) from `tec_tenant_subscriptions` + `tec_tenant_payments` + `tec_subscription_plans`: completed payments → `paid`, failed/refunded → `cancelled`, and the current period (`next_billing_date`/`subscription_end_date`) → `pending`/`overdue` with amount = plan price by `billing_cycle` (trials generate none). Tenant admins (`AdminGuard`, tenant-scoped) use `GET /api/billing/invoices`, `GET /api/billing/current-invoice` and `POST /api/billing/pay`; `pay` only creates a `pending` payment (notes carry `Solicitud del tenant · <invoice_number>`) and never handles card data (no PCI). Super admin confirms via `PATCH /api/tenant-management/payments/:id/confirm`, which flips the payment to `completed` and reuses `applyCompletedPayment` (subscription `active`, +1 month/year, last payment). Plan prices are final (no tax); invoice PDF is client-side printing of the detail modal. **Bold checkout (v0.3.43)**: `BoldService` uses Bold's API Link de pagos (`POST /online/link/v1`, header `Authorization: x-api-key <BOLD_API_KEY>`, body `amount_type=CLOSE`, `amount.currency=COP`, `reference` = invoice number **plus a base36 timestamp suffix** (Bold rejects reused references with `PL_000`), `callback_url`); active links (`ACTIVE`/`PROCESSING`) return the stored `checkout_url` unchanged and a dead link (`REJECTED`/`CANCELLED`/`EXPIRED`) reuses the same `tec_tenant_payments` row with the new `LNK_*` (Option A) instead of erroring. `POST /api/billing/pay-bold` creates a `pending` `tec_tenant_payments` row with `bold_payment_id` = `LNK_*` (unique) and `invoice_url` = checkout URL, then the UI redirects to Bold. Public webhook `POST /api/webhooks/bold` verifies `x-bold-signature` = HMAC-SHA256(secret, base64(raw body)) and is idempotent (already-completed row → 200); **the secret is `BOLD_WEBHOOK_SECRET` when set, otherwise `BOLD_API_KEY`** (Bold signs with the identity key; empty only in sandbox, fail-closed otherwise, detected via `BOLD_SANDBOX=true` or a base URL containing `sandbox`). A placeholder/empty `BOLD_API_KEY` disables the gateway (503, fail-closed). `SALE_APPROVED` settles via `confirmPayment` (idempotent by status; **amount verified against `data.amount.total`**, mismatch logs `payment_amount_mismatch` and never activates) and `SALE_REJECTED` marks the row `failed`; the webhook matches by `bold_payment_id`, `invoice_url` or `notes` (covers `reference=null`) and the confirmation activity log records `source: bold_webhook|bold_verify|manual`. Bold can delay link webhooks up to 10 min, so `POST /api/billing/verify-bold` queries `GET /online/link/v1/{LNK}` on return (`?payment=return|success|cancelled`) and settles PAID/REJECTED/CANCELLED/EXPIRED. Card data never reaches the API. Requires `docs/migrations/v0.3.43-bold.sql` (`bold_payment_id`) and the `BOLD_*` env vars.
- POS/Products scanning (v0.3.24, extended to `/productos` in v0.3.27): `web/src/components/ProductScanner.tsx` uses `html5-qrcode` (loaded with a dynamic import so it is code-split) for EAN-13/EAN-8/UPC-A/UPC-E/Code-128/Code-39/ITF/Codabar and QR. The camera starts only when the modal opens and **must** be stopped + cleared on close. Scanned values are parsed by the shared `web/src/scan.ts` `parseScanValue` (raw text, JSON `code|barcode|sku|id`, or URL with `code`/`barcode`/last path segment); POS resolves client-side against `GET /api/catalog/products?store_id&q=` (exact `code`, then exact `name`) using the same `addToCart` rules, while Products resolves against `GET /api/products?store_id&q=` (exact `code`), filters the table by the scanned code and, when not found, prefills `code` for "+ Crear producto" with the scanned value; the product create/edit modal's **Código** field also has its own 📷/🔳 buttons that fill the code and focus Nombre (list-level vs modal-level behavior switches on `modalOpen`). Duplicate reads within 2 s are ignored. There is no backend barcode endpoint or card data involved; manual entry is the fallback when the camera is unavailable/denied (HTTPS required). Continuous mode keeps the modal open and counts scans. **v0.3.85**: every stop/clear goes through `safeStopScanner()` (try/catch around `stop()`/`clear()`); html5-qrcode throws synchronously ("Cannot stop, scanner is not running or paused.") when the camera never started (no device/permission) and, with no error boundary, that cleanup exception unmounted the whole React app — closing the scanner on a camera-less device blanked the POS (caught by the Playwright E2E running headless).
- Overdue enforcement (v0.3.47, no DDL): `TenantManagementService.refreshOverdueStatuses()` runs **hourly** (together with `refreshLifecycleStatuses`): with `BILLING_AUTO_SUSPEND=true` it suspends every `active` subscription whose `COALESCE(next_billing_date, subscription_end_date) < CURRENT_DATE - BILLING_GRACE_DAYS` (regardless of `auto_renew`), sets the tenant `inactive`, **deletes its `tec_sessions`** and logs `subscription_suspended`; with the flag `false` it only warns. `TenantOperationalGuard` (class-level on `SalesController`) returns **402** `{ error: 'Payment Overdue' }` for non-GET requests (create sale, payments, update/delete sale) while all GET requests stay allowed (read-only); subscription state is cached 60 s via `operationalState()`. Paying through any channel reactivates the tenant inside `applyCompletedPayment` (tenant `inactive` → `active`); manual `suspendTenant` also deletes sessions.
- Product categories (v0.3.52, `api/src/categories/`, approved DDL `docs/migrations/v0.3.52-categories.sql`): `tec_categories` is per-tenant with `UNIQUE (tenant_id, name)` and `tec_products.category_id` is nullable. `/api/categories` is admin-only and strictly tenant-scoped (GET/POST/PUT/DELETE); duplicate names return 400, deletion is blocked while products are linked (count checked first), and product create/update validate the category with `assertCategory` (must exist in the tenant; `category_id: null` clears it on update). The managed-products list returns `category_id` + `category_name`; web has `/categorias`, the sidebar item and a "Categoría" select in the product modal. Category ids are matched as text (`id::text = $2`) so the API works whether `tec_categories.id` is `uuid` (migration) or numeric/serial, and product `category_id` accepts both forms; the error message for a bad id includes the received value.
- Inventory (v0.3.58): `tec_products.quantity` (NOT NULL default 0, global per tenant) is the **only** source of truth. Sales create/edit/delete, purchases create/edit and `PUT /api/products/:id/stock` read/write it inside transactions (`UPDATE ... SET quantity = quantity ± n WHERE ... AND quantity >= n`); the POS catalog returns `available_quantity` from it and the products list uses `p.price`/`p.quantity` only (no store joins). `tec_product_store_qty` is legacy: it is **not dropped** (the PHP POS may still use it), but the API ignores it completely and there are **no sync triggers** (the v0.3.57 ones were removed by `docs/migrations/v0.3.58-drop-inventory-sync.sql`). Consequence: stock is global, so multi-store tenants share one quantity per product; the legacy table drifts independently.
- Customer auth & points (v0.3.59, approved DDL `docs/migrations/v0.3.59-customer-auth-and-points.sql`): `tec_customers` gains `password varchar(255)` (hash only — never store or log plaintext) and `points_balance integer DEFAULT 0` (nullable; read/write with `COALESCE(points_balance, 0)` and insert `0` explicitly). Customer login is case-insensitive on email (`LOWER(email) = LOWER($1)`, served by the functional index `idx_tec_customers_email_lower`) and digits-only on phone (normalize on write; the login endpoint strips non-digits from the input before comparing). **Legacy `phone` data is dirty** (empty strings, spaces, dashes, mixed formats), so legacy rows may not match a digits-only lookup until a one-time normalization backfill is run. The API never runs this DDL; the operator runs the script once before deploying.
- Customer points & auth (v0.3.60, approved DDL `docs/migrations/v0.3.60-remove-points-trigger.sql` + one-time DML `docs/migrations/v0.3.60-backfill-customer-points.sql`): the legacy DB trigger `trg_acreditar_puntos_venta` on `tec_sales` is removed; **the API owns points inside the sale transaction**. `SalesService.create` credits `points_balance` only when the sale has a `customer_id` and status is `paid`/`partial`; `addPayment` credits only when a `due` sale transitions to `paid`/`partial`; `update` applies the delta (`creditedNew − creditedOld`, including customer changes); `remove` reverses the credited amount; balances clamp at 0 via `GREATEST`. The `point_transactions` ledger is intentionally **not** used (it has no `customer_id`/`sale_id`/`tenant_id`; adding them is unapproved DDL). The backfill resets all balances and recomputes from `paid`/`partial` sales; the operator runs it once, after the trigger removal and API deploy, in a maintenance window. Customer auth is **stateless JWT**: `POST /api/auth/customer-login` (identity = email or phone, digits-only normalization), `POST /api/auth/customer-set-password` (claims a `NULL` password once; 400 "Account already has a password..." if set; atomic `UPDATE ... WHERE password IS NULL`), `GET /api/auth/customer-me` (there is no DB session for customers — no `tec_sessions` row and no `sid`). Customer tokens carry `type: 'customer'`; `JwtAuthGuard` accepts both types (POS tokens still require `sid`), `TenantContextGuard` stays POS-only and rejects customer tokens, and the new `CustomerContextGuard` rejects POS tokens. Customer passwords are always bcrypt (`USER_PASSWORD_METHOD` is legacy-only for the shared `tec_users`); ambiguous identities (>1 exact match) fail as invalid credentials; login/set-password failures share the `tec_login_attempts` lockout. `CustomersService` normalizes phone to digits on create/update; the phone login lookup uses `regexp_replace(phone, '[^0-9]', '', 'g') = $1` so dirty legacy phones still match (the plain `idx_tec_customers_phone` index is not used by that branch).
- Customer app endpoints (v0.3.60, `api/src/customer/`, no DDL): `GET /api/customer/profile` (customer data + `points_balance` + last 5 `paid`/`partial` sales with points — no ledger history), `PUT /api/customer/profile` (`{ name?, email?, phone? }`; tenant+customer come from the token, `tec_customers` has a single `name` column — no first/last split — phone is stored digits-only, empty/absent values keep the current data, email validated with `@IsEmail`), `GET /api/customer/stores` (tenant stores for the app selector), `GET /api/customer/products?store_id&q&category_id` (reuses `CatalogService.listProducts`, which also returns `reward_points`; the optional `category_id` accepts a UUID (v0.3.52 schema) or a numeric id, is ANDed with `q`, and invalid values return 400), `GET /api/customer/categories` (customer category list `{ id, name }` from `tec_categories` ordered by name ASC, max 200; fail-safe `to_regclass` probe with a 60 s cache returns `[]` when the table is missing, same pattern as banners), `GET /api/customer/rewards` (MVP Premios catalog: tenant products with `reward_points > 0` via `CatalogService.listRewardProducts`, ordered by name, max 100; `reward_points` doubles as the required-points value because `es_premio`/`descuento_premio` do not exist and adding them is unapproved DDL; **redemption is not implemented** — the Flutter app shows a "Próximamente" badge and no points are spent), `GET /api/customer/orders?page&limit` (max 50, newest first), `GET /api/customer/orders/:id` (items + payments + totals, 404 if the sale belongs to another customer), and `POST /api/customer/checkout` — all guarded by `JwtAuthGuard` + `CustomerContextGuard`; tenant and customer always come from the token, never from the request body. Checkout reuses the private `SalesService.createSale` core (stock, prices, tax, points) via `createForCustomer`: payload is only `{ items: [{ product_id, quantity }], store_id? }` (no discounts, payments or prices), `customer_id` is forced from the token, `created_by` is **NULL** (app order, not a POS employee) and `user_id` stays NULL. Store resolution: requested `store_id` must exist in the tenant, else the customer's `store_id` if valid, else the tenant's first store; app customers may order from any store of their tenant (`customerStoreScoped: false`; POS staff keep the store-scoped customer check). Since checkout sends no payment, orders are created `status='due'`, so points are credited only when a POS/staff payment flips them to `paid`/`partial` via `addPayment`.
- Category images (v0.3.66, optional DDL `docs/migrations/v0.3.66-category-image.sql`): `tec_categories.image_url varchar(500)` (nullable) powers the app's circular category buttons. `CategoriesService` probes `information_schema.columns` (60 s cache) and selects `c.image_url` when the column exists or `NULL::text AS image_url` otherwise, so `/api/categories` (POS admin) and `/api/customer/categories` keep working before the migration runs; the customer response is `{ id, name, image_url }` and the app falls back to a letter circle when there is no image. `create` returns `image_url: null` (the POS admin UI has no image field yet — set images via SQL or a future admin field).
- Customer banners (no DDL, `api/src/customer/banners.service.ts`): `GET /api/customer/banners` (`JwtAuthGuard` + `CustomerContextGuard`) returns `{ id, title: null, image_url, target_url: null }`, max 20. The live `public.banners` table (confirmed) is **global** and only has `id bigint`, `image_url text NULL`, `created_at timestamptz` — there is **no tenant/title/target_url/active/priority** — so rows are filtered by `image_url IS NOT NULL AND btrim(image_url) <> ''`, ordered `created_at DESC, id DESC`, and the carousel renders images only (no deep links). `BannersService` only probes table existence (`to_regclass`, 60 s cache) and returns `[]` when the table is missing, so the API never 500s; titles/deep links/tenant scoping would require new columns (unapproved DDL).
- Customer checkout with payment (no DDL, `api/src/payments/`): `POST /api/customer/checkout-with-payment` (`JwtAuthGuard` + `CustomerContextGuard`) takes `{ items, store_id?, payment_method: 'cash'|'bold'|'addi'|'sistecredito' }`, creates the sale with `SalesService.createForCustomer` (always `due`) and returns `{ order_id, status, payment_url, payment_method }`. `cash` → no URL; `bold` → `TenantBoldService.createLink` (v0.3.78) using the **tenant's own Bold identity key** with reference `ORDER-<saleId>-<base36 timestamp>` and callback = tenant `return_url` ?? `CUSTOMER_PAYMENT_RETURN_URL`; `addi` → real Custom Integrations client **`AddiService` (v0.3.79, `api/src/payments/addi.service.ts`)**: OAuth2 client-credentials (Auth0) with `client_id` = tenant `addi_api_key`, `client_secret` = tenant `addi_webhook_secret`, `audience` = `ADDI_AUDIENCE`, endpoint `ADDI_AUTH_URL` (accepts base or full URL — normalized to `/oauth/token`, double slashes collapsed; token request is `application/x-www-form-urlencoded` per Auth0, v0.3.80); the JWT is cached per tenant (`expires_in` − 5 min, invalidated on a 401). Checkout (v0.3.82 payload snake_case): `POST {ADDI_API_BASE_URL}{ADDI_APPLICATIONS_PATH}` with `redirect: 'manual'`, order reference `ORDER-<saleId>-<base36 ts>` (unique per attempt), integer COP `amount`, nested `customer` (`first_name`/`last_name` from the split name, `email`, `phone` normalized to `57XXXXXXXXXX` (country code, **no `+` sign** — v0.3.84) via `normalizePhoneForAddi`, `document_type: 'CC'`, `document_number` from `ADDI_TEST_DOCUMENT_NUMBER`, default `1001234567`, until a real document field exists in `tec_customers`), a `shipping` block (same name/phone + `address: Calle Falsa 123`, `city: Bogotá`, `country: 'CO'` until the app checkout sends an address from `customer_addresses`; disable with `ADDI_SEND_SHIPPING=false` to isolate payload 400s) and `items` loaded from `tec_sale_items` ⋈ `tec_products` (`sku` = `code` ?? `PROD-<id>`, `name`, integer `quantity`, integer `price` from `unit_price`); `callback_url` = `ADDI_CALLBACK_URL` and **`redirection_url` is always present** (tenant `return_url` ?? `CUSTOMER_PAYMENT_RETURN_URL` ?? default `https://pos.tienderu.com/config?payment=return`); the checkout URL comes from the 301 `Location` header (defensive fallback: 2xx JSON `checkout_url`/`url`). The exact payload is logged at debug right before the fetch (both `customer` and `shipping` PII masked via `maskEmail`/`maskPhone` **only in the log copy** — the request body sent to Addi always carries the real, unmasked, +57-normalized values) and any non-2xx logs Addi's **complete** response body **plus the parsed `errors[]` array** and the `x-trace-id` header when present (for Addi support).
