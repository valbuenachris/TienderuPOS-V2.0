# POS v2 development rules

- This is a clean TypeScript/NestJS + React POS. Do not copy PHP/CodeIgniter implementation files here; `../pos-gres` remains the legacy reference until cutover.
- `tec_tenants` is the approved tenant registry (the only approved DDL): `id uuid, name, host, status ('active'|'inactive'), created_at`. The v0.3.11 tenant-management tables (`tec_subscription_plans`, `tec_tenant_subscriptions`, `tec_tenant_payments`, `tec_tenant_activity_logs`) are an approved DDL exception too; their only script is `docs/migrations/v0.3.11-tenant-management.sql` and the operator runs it before deploying (the API never runs DDL). Super admin is a shared `tec_groups` row `name='super_admin'` (`tenant_id IS NULL`) plus a `tec_users` row in the default tenant. `AdminGuard` accepts `admin` and `super_admin`; `SuperAdminGuard` protects global endpoints (`GET/POST /api/tenants`, `/api/tenant-management/*`, `POST /api/auth/switch-tenant`). **Every token carries `home_tenant_id`** (equals `tenant_id` on login; on `switch-tenant` it stays the home tenant while `tenant_id` is the target) and **`super: true` when the user's resolved group is `super_admin`**. The session payload mirrors `homeTenantId` and `super`, and `TenantContextGuard` rejects any mismatch; cross-tenant scope additionally requires `claims.super === true` AND the resolved group `super_admin`. `GET /api/auth/me` returns `super: boolean`. Audit stays in API logs for now. The web keeps a session-only `selectedTenantId`: a super admin login starts in **global view** (dropdown shows "Seleccionar tenant…", the sidebar header shows the generic "Tienderu POS · Manager" instead of any tenant settings, the sidebar lists only Dashboard global and Gestión de tenants —Tenants/Planes/Pagos/Datos—, and tenant-scoped routes including `/config` redirect to `/dashboard/global`); picking a tenant runs `switch-tenant` and reveals the full POS menu; clearing the dropdown returns to global view. `/config` is tenant-scoped, never shown in global view. Non-super users are never gated and always see the POS menu.
- The Supabase schema is immutable. Do not add migrations, alter tables, create indexes, change policies/grants, or enable ORM schema synchronization. **Database triggers/rules on stock tables are forbidden**: the API owns all stock math inside transactions; an enabled trigger double-applies deductions/additions. Exception: the only allowlisted trigger is `trg_calculate_reward_points`; `DatabaseService` logs an error at startup if it finds any other enabled trigger on `tec_sales`, `tec_sale_items`, `tec_products`, `tec_purchases` or `tec_purchase_items`.
- Use the typed `SupabaseService` for simple table CRUD and types in `api/src/database/database.types.ts`; use `pg` for atomic multi-table sales, BYTEA session compatibility, and exact-text monetary reports. Type every SQL result from the known table row types or an explicit aggregate projection.
- Keep database/service-role credentials in the API `.env` only. React uses the Nest API and TanStack Query for server state; do not fetch server data with `useEffect` or connect the browser directly to Supabase.
- All tenant-owned SQL must use `tenant_id` from the verified JWT/tenant resolver. Never accept a tenant ID or database credential from browser input.
- Authentication and store scope use `tec_users` plus its tenant-matched `tec_groups` row; `group_name = 'admin'` can select tenant stores, while a cashier is limited to `tec_users.store_id`.
- POS staff authenticate from `public.tec_users`; customers are `public.tec_customers`. For sales, `created_by` is the POS employee, `customer_id` is the customer, and `user_id` stays unused/null. The POS customer picker searches server-side via `GET /api/catalog/customers?q=` (matches name/email/phone within the tenant/store, max 100 rows, UI debounces 300 ms and shows 10); "Cliente ocasional" sends no `customer_id`.
- Payment methods (`paid_by` in `tec_payments`) are restricted to `cash`, `CC`, `Transferencia`, `Sistecredito`, `ADI` and `credito` (legacy-compatible casing; `Sistecredito`/`ADI` are what the old POS writes). `due` records no payment and leaves `status = due`; cash can register a partial payment. The POS label "Crédito [tienda]" maps to the stable value `credito`; never store tenant/store names in `paid_by`.
- The POS confirms every sale in `SaleConfirmationModal` before calling `POST /api/sales`. Cash may send `amount_received` (and optional `change_amount`, which must equal `amount_received - total`); the server applies `paid = min(amount_received, grand_total)` so `tec_sales.paid` and `tec_payments.amount` never exceed the total, returns `change_amount`, and computes `status` itself. Never trust a client-sent `status`, and never persist change (the immutable schema has no column for it).
- Manual discounts: `discount_type` (`fixed`|`percent`) + `discount_value` (decimal string). Percent applies over `subtotal + tax` and must be ≤ 100; fixed must be ≥ 0 and ≤ the pre-discount total. Store the amount in `order_discount`, the raw value in `order_discount_id` (`"10%"` or the amount), `total_discount = order_discount`, `product_discount = 0`, and populate `product_tax`/`total_tax`/`order_tax`/`order_tax_id`/`rounding`. Sale `update` must reapply the stored discount (percent recalculated, fixed kept) so `grand_total` stays consistent.
- The POS ticket is rendered by `web/src/components/SaleTicket.tsx` and printed at 58 mm via the `.print-receipt` container (`@media print` hides everything else, `@page size: 58mm auto`). The QR is generated in the browser with the `qrcode` package from the sale payload; do not add a backend QR endpoint or send sale data to third parties. The same component is reused for the on-screen preview modal (`preview` prop), which also offers WhatsApp (formatted plain text, `customer_phone` from `create`/`detail`, +57 for 10-digit Colombian numbers, WhatsApp Web fallback) and PDF (`html2pdf.js`, 58 mm) actions. The actions render only with `preview` so the hidden print node stays clean (the PDF captures only the ticket node, not the buttons). The footer ends with a two-line branding block: `Facturado con Tienderu POS` + `email - teléfono` (from `settings.email`/`settings.phone`, falling back to `info@tienderu.com` · `3104039092`).
- IDs use existing identity/sequences; omit `id` on inserts and use `RETURNING id`. Primary keys are global; do not allocate `MAX(id)+1` per tenant.
- Tenant branding (v0.3.74): the per-tenant logo lives in `tec_tenant_settings.logo_url` (no new DDL; the `tec_tenants` registry stays untouched). Upload/delete remain in `POST/DELETE /api/settings/logo` (admin-only, Supabase Storage `productos/logos/<tenant>_<ts>.<ext>`, 2 MB, PNG/JPG/WEBP/SVG, previous file removed). `GET /customer/profile` now also returns `tenant: { id, name, logo_url }` (graceful fallback if the settings row/table is missing) so the mobile app caches the URL in SharedPreferences and shows it on the login screen and home AppBar (fallback to the default icon). The web sidebar renders `settings.logo_url` (max-height 40px, fallback letter "P").
- Per-tenant settings live in `public.tec_tenant_settings` (approved DDL, v0.3.16; script `docs/migrations/v0.3.16-tenant-settings.sql`): one row per tenant (`tenant_id` UNIQUE) with branding, fiscal/contact fields, currency/timezone/language, taxes and ticket fields. Never expose SMTP secrets. `SettingsService` detects the table at startup and **re-checks lazily every 30 s**, so it switches to per-tenant mode without an API restart once the migration is applied; when present it reads/writes **only the active tenant's row** (provisioning it with `site_name` = tenant name if missing) and the tenant bootstrap ensures the row too; when absent it falls back to the legacy global `tec_settings` (introspected columns, 30 s cache, first/shared row). `assertTenant` validates that the tenant exists (non-deleted) — it must not require POS users. `GET /api/settings` (full editable set + `supported`), `PUT /api/settings` and logo upload/delete are admin-only (`AdminGuard` accepts admin+super_admin); `GET /api/settings/pos` is authenticated and returns only the POS display subset (`POS_DISPLAY_COLUMNS`) that the session/ticket need. Logo uploads go to `SUPABASE_PRODUCT_BUCKET` under `logos/` and require `logo_url`.
- Tenant creation (`POST /api/tenants`, super-admin) is transactional bootstrap: inserts `tec_tenants`, a default store (`Tienda Principal`, code `MAIN`), a default admin user linked to the shared `admin` group (username `<slug>_admin` with `_1`, `_2`… on collision, checked globally, slug ≤20 chars; generated password hashed with `USER_PASSWORD_METHOD`/`BCRYPT_ROUNDS` via `api/src/common/password.ts`) **and** a subscription — a 14-day trial for free/default plans, or an active monthly subscription (start today, `subscription_end_date`/`next_billing_date` +1 month) when the chosen `plan_id` is paid (price > 0) — logging `tenant_created`. The plain password is returned **only once** in the creation response; never log or persist it. `PATCH /api/tenants/:id` (super-admin) updates `name`/`host`/`status`, allows clearing the host with `null`; `host` is informational and has **no uniqueness enforcement** (single-domain model, all tenants may share `pos.tienderu.com`). `DELETE /api/tenants/:id` (super-admin) is a **soft delete** (`status='deleted'`, `host=NULL`, 204), logs `tenant_deleted` and only proceeds when the tenant has no sales, no active non-admin users and no store inventory; the active tenant cannot delete itself. Admin/staff groups are shared (`tenant_id IS NULL`) so no per-tenant groups are created. Never resolve a store from `user.store_id` without checking it exists in the active tenant's `stores` list (super admin may carry a store from another tenant).
- Login is **credential-based** (single-domain SaaS): `AuthService.login` looks up the user by username/email across `tec_users` (case-insensitive, active only) and uses that row's `tenant_id`; the HTTP Host header is never used to pick a tenant. Ambiguous (>1 exact match) or unknown identities fail as invalid credentials (no tenant enumeration), and `inactive`/`deleted` tenants are rejected. `TENANT_HOST_MAP`/`DEFAULT_TENANT_ID` remain only as a fallback bucket for lockout attempts of unknown identities. Keep this behavior when touching `AuthService.login`.
- Tenant billing (v0.3.23, `api/src/billing/`): invoices are **derived** (no DDL) from `tec_tenant_subscriptions` + `tec_tenant_payments` + `tec_subscription_plans`: completed payments → `paid`, failed/refunded → `cancelled`, and the current period (`next_billing_date`/`subscription_end_date`) → `pending`/`overdue` with amount = plan price by `billing_cycle` (trials generate none). Tenant admins (`AdminGuard`, tenant-scoped) use `GET /api/billing/invoices`, `GET /api/billing/current-invoice` and `POST /api/billing/pay`; `pay` only creates a `pending` payment (notes carry `Solicitud del tenant · <invoice_number>`) and never handles card data (no PCI). Super admin confirms via `PATCH /api/tenant-management/payments/:id/confirm`, which flips the payment to `completed` and reuses `applyCompletedPayment` (subscription `active`, +1 month/year, last payment). Plan prices are final (no tax); invoice PDF is client-side printing of the detail modal. **Bold checkout (v0.3.43)**: `BoldService` uses Bold's API Link de pagos (`POST /online/link/v1`, header `Authorization: x-api-key <BOLD_API_KEY>`, body `amount_type=CLOSE`, `amount.currency=COP`, `reference` = invoice number **plus a base36 timestamp suffix** (Bold rejects reused references with `PL_000`), `callback_url`); active links (`ACTIVE`/`PROCESSING`) return the stored `checkout_url` unchanged and a dead link (`REJECTED`/`CANCELLED`/`EXPIRED`) reuses the same `tec_tenant_payments` row with the new `LNK_*` (Option A) instead of erroring. `POST /api/billing/pay-bold` creates a `pending` `tec_tenant_payments` row with `bold_payment_id` = `LNK_*` (unique) and `invoice_url` = checkout URL, then the UI redirects to Bold. Public webhook `POST /api/webhooks/bold` verifies `x-bold-signature` = HMAC-SHA256(secret, base64(raw body)) and is idempotent (already-completed row → 200); **the secret is `BOLD_WEBHOOK_SECRET` when set, otherwise `BOLD_API_KEY`** (Bold signs with the identity key; empty only in sandbox, fail-closed otherwise, detected via `BOLD_SANDBOX=true` or a base URL containing `sandbox`). A placeholder/empty `BOLD_API_KEY` disables the gateway (503, fail-closed). `SALE_APPROVED` settles via `confirmPayment` (idempotent by status; **amount verified against `data.amount.total`**, mismatch logs `payment_amount_mismatch` and never activates) and `SALE_REJECTED` marks the row `failed`; the webhook matches by `bold_payment_id`, `invoice_url` or `notes` (covers `reference=null`) and the confirmation activity log records `source: bold_webhook|bold_verify|manual`. Bold can delay link webhooks up to 10 min, so `POST /api/billing/verify-bold` queries `GET /online/link/v1/{LNK}` on return (`?payment=return|success|cancelled`) and settles PAID/REJECTED/CANCELLED/EXPIRED. Card data never reaches the API. Requires `docs/migrations/v0.3.43-bold.sql` (`bold_payment_id`) and the `BOLD_*` env vars.
- POS/Products scanning (v0.3.24, extended to `/productos` in v0.3.27): `web/src/components/ProductScanner.tsx` uses `html5-qrcode` (loaded with a dynamic import so it is code-split) for EAN-13/EAN-8/UPC-A/UPC-E/Code-128/Code-39/ITF/Codabar and QR. The camera starts only when the modal opens and **must** be stopped + cleared on close. Scanned values are parsed by the shared `web/src/scan.ts` `parseScanValue` (raw text, JSON `code|barcode|sku|id`, or URL with `code`/`barcode`/last path segment); POS resolves client-side against `GET /api/catalog/products?store_id&q=` (exact `code`, then exact `name`) using the same `addToCart` rules, while Products resolves against `GET /api/products?store_id&q=` (exact `code`), filters the table by the scanned code and, when not found, prefills `code` for "+ Crear producto" with the scanned value; the product create/edit modal's **Código** field also has its own 📷/🔳 buttons that fill the code and focus Nombre (list-level vs modal-level behavior switches on `modalOpen`). Duplicate reads within 2 s are ignored. There is no backend barcode endpoint or card data involved; manual entry is the fallback when the camera is unavailable/denied (HTTPS required). Continuous mode keeps the modal open and counts scans.
- Overdue enforcement (v0.3.47, no DDL): `TenantManagementService.refreshOverdueStatuses()` runs **hourly** (together with `refreshLifecycleStatuses`): with `BILLING_AUTO_SUSPEND=true` it suspends every `active` subscription whose `COALESCE(next_billing_date, subscription_end_date) < CURRENT_DATE - BILLING_GRACE_DAYS` (regardless of `auto_renew`), sets the tenant `inactive`, **deletes its `tec_sessions`** and logs `subscription_suspended`; with the flag `false` it only warns. `TenantOperationalGuard` (class-level on `SalesController`) returns **402** `{ error: 'Payment Overdue' }` for non-GET requests (create sale, payments, update/delete sale) while all GET requests stay allowed (read-only); subscription state is cached 60 s via `operationalState()`. Paying through any channel reactivates the tenant inside `applyCompletedPayment` (tenant `inactive` → `active`); manual `suspendTenant` also deletes sessions.
- Product categories (v0.3.52, `api/src/categories/`, approved DDL `docs/migrations/v0.3.52-categories.sql`): `tec_categories` is per-tenant with `UNIQUE (tenant_id, name)` and `tec_products.category_id` is nullable. `/api/categories` is admin-only and strictly tenant-scoped (GET/POST/PUT/DELETE); duplicate names return 400, deletion is blocked while products are linked (count checked first), and product create/update validate the category with `assertCategory` (must exist in the tenant; `category_id: null` clears it on update). The managed-products list returns `category_id` + `category_name`; web has `/categorias`, the sidebar item and a "Categoría" select in the product modal. Category ids are matched as text (`id::text = $2`) so the API works whether `tec_categories.id` is `uuid` (migration) or numeric/serial, and product `category_id` accepts both forms; the error message for a bad id includes the received value.
- Inventory (v0.3.58): `tec_products.quantity` (NOT NULL default 0, global per tenant) is the **only** source of truth. Sales create/edit/delete, purchases create/edit and `PUT /api/products/:id/stock` read/write it inside transactions (`UPDATE ... SET quantity = quantity ± n WHERE ... AND quantity >= n`); the POS catalog returns `available_quantity` from it and the products list uses `p.price`/`p.quantity` only (no store joins). `tec_product_store_qty` is legacy: it is **not dropped** (the PHP POS may still use it), but the API ignores it completely and there are **no sync triggers** (the v0.3.57 ones were removed by `docs/migrations/v0.3.58-drop-inventory-sync.sql`). Consequence: stock is global, so multi-store tenants share one quantity per product; the legacy table drifts independently.
- Customer auth & points (v0.3.59, approved DDL `docs/migrations/v0.3.59-customer-auth-and-points.sql`): `tec_customers` gains `password varchar(255)` (hash only — never store or log plaintext) and `points_balance integer DEFAULT 0` (nullable; read/write with `COALESCE(points_balance, 0)` and insert `0` explicitly). Customer login is case-insensitive on email (`LOWER(email) = LOWER($1)`, served by the functional index `idx_tec_customers_email_lower`) and digits-only on phone (normalize on write; the login endpoint strips non-digits from the input before comparing). **Legacy `phone` data is dirty** (empty strings, spaces, dashes, mixed formats), so legacy rows may not match a digits-only lookup until a one-time normalization backfill is run. The API never runs this DDL; the operator runs the script once before deploying.
- Customer points & auth (v0.3.60, approved DDL `docs/migrations/v0.3.60-remove-points-trigger.sql` + one-time DML `docs/migrations/v0.3.60-backfill-customer-points.sql`): the legacy DB trigger `trg_acreditar_puntos_venta` on `tec_sales` is removed; **the API owns points inside the sale transaction**. `SalesService.create` credits `points_balance` only when the sale has a `customer_id` and status is `paid`/`partial`; `addPayment` credits only when a `due` sale transitions to `paid`/`partial`; `update` applies the delta (`creditedNew − creditedOld`, including customer changes); `remove` reverses the credited amount; balances clamp at 0 via `GREATEST`. The `point_transactions` ledger is intentionally **not** used (it has no `customer_id`/`sale_id`/`tenant_id`; adding them is unapproved DDL). The backfill resets all balances and recomputes from `paid`/`partial` sales; the operator runs it once, after the trigger removal and API deploy, in a maintenance window. Customer auth is **stateless JWT**: `POST /api/auth/customer-login` (identity = email or phone, digits-only normalization), `POST /api/auth/customer-set-password` (claims a `NULL` password once; 400 "Account already has a password..." if set; atomic `UPDATE ... WHERE password IS NULL`), `GET /api/auth/customer-me` (there is no DB session for customers — no `tec_sessions` row and no `sid`). Customer tokens carry `type: 'customer'`; `JwtAuthGuard` accepts both types (POS tokens still require `sid`), `TenantContextGuard` stays POS-only and rejects customer tokens, and the new `CustomerContextGuard` rejects POS tokens. Customer passwords are always bcrypt (`USER_PASSWORD_METHOD` is legacy-only for the shared `tec_users`); ambiguous identities (>1 exact match) fail as invalid credentials; login/set-password failures share the `tec_login_attempts` lockout. `CustomersService` normalizes phone to digits on create/update; the phone login lookup uses `regexp_replace(phone, '[^0-9]', '', 'g') = $1` so dirty legacy phones still match (the plain `idx_tec_customers_phone` index is not used by that branch).
- Customer app endpoints (v0.3.60, `api/src/customer/`, no DDL): `GET /api/customer/profile` (customer data + `points_balance` + last 5 `paid`/`partial` sales with points — no ledger history), `PUT /api/customer/profile` (`{ name?, email?, phone? }`; tenant+customer come from the token, `tec_customers` has a single `name` column — no first/last split — phone is stored digits-only, empty/absent values keep the current data, email validated with `@IsEmail`), `GET /api/customer/stores` (tenant stores for the app selector), `GET /api/customer/products?store_id&q&category_id` (reuses `CatalogService.listProducts`, which also returns `reward_points`; the optional `category_id` accepts a UUID (v0.3.52 schema) or a numeric id, is ANDed with `q`, and invalid values return 400), `GET /api/customer/categories` (customer category list `{ id, name }` from `tec_categories` ordered by name ASC, max 200; fail-safe `to_regclass` probe with a 60 s cache returns `[]` when the table is missing, same pattern as banners), `GET /api/customer/rewards` (MVP Premios catalog: tenant products with `reward_points > 0` via `CatalogService.listRewardProducts`, ordered by name, max 100; `reward_points` doubles as the required-points value because `es_premio`/`descuento_premio` do not exist and adding them is unapproved DDL; **redemption is not implemented** — the Flutter app shows a "Próximamente" badge and no points are spent), `GET /api/customer/orders?page&limit` (max 50, newest first), `GET /api/customer/orders/:id` (items + payments + totals, 404 if the sale belongs to another customer), and `POST /api/customer/checkout` — all guarded by `JwtAuthGuard` + `CustomerContextGuard`; tenant and customer always come from the token, never from the request body. Checkout reuses the private `SalesService.createSale` core (stock, prices, tax, points) via `createForCustomer`: payload is only `{ items: [{ product_id, quantity }], store_id? }` (no discounts, payments or prices), `customer_id` is forced from the token, `created_by` is **NULL** (app order, not a POS employee) and `user_id` stays NULL. Store resolution: requested `store_id` must exist in the tenant, else the customer's `store_id` if valid, else the tenant's first store; app customers may order from any store of their tenant (`customerStoreScoped: false`; POS staff keep the store-scoped customer check). Since checkout sends no payment, orders are created `status='due'`, so points are credited only when a POS/staff payment flips them to `paid`/`partial` via `addPayment`.
- Category images (v0.3.66, optional DDL `docs/migrations/v0.3.66-category-image.sql`): `tec_categories.image_url varchar(500)` (nullable) powers the app's circular category buttons. `CategoriesService` probes `information_schema.columns` (60 s cache) and selects `c.image_url` when the column exists or `NULL::text AS image_url` otherwise, so `/api/categories` (POS admin) and `/api/customer/categories` keep working before the migration runs; the customer response is `{ id, name, image_url }` and the app falls back to a letter circle when there is no image. `create` returns `image_url: null` (the POS admin UI has no image field yet — set images via SQL or a future admin field).
- Customer banners (no DDL, `api/src/customer/banners.service.ts`): `GET /api/customer/banners` (`JwtAuthGuard` + `CustomerContextGuard`) returns `{ id, title: null, image_url, target_url: null }`, max 20. The live `public.banners` table (confirmed) is **global** and only has `id bigint`, `image_url text NULL`, `created_at timestamptz` — there is **no tenant/title/target_url/active/priority** — so rows are filtered by `image_url IS NOT NULL AND btrim(image_url) <> ''`, ordered `created_at DESC, id DESC`, and the carousel renders images only (no deep links). `BannersService` only probes table existence (`to_regclass`, 60 s cache) and returns `[]` when the table is missing, so the API never 500s; titles/deep links/tenant scoping would require new columns (unapproved DDL).
- Customer checkout with payment (no DDL, `api/src/payments/`): `POST /api/customer/checkout-with-payment` (`JwtAuthGuard` + `CustomerContextGuard`) takes `{ items, store_id?, payment_method: 'cash'|'bold'|'addi'|'sistecredito' }`, creates the sale with `SalesService.createForCustomer` (always `due`) and returns `{ order_id, status, payment_url, payment_method }`. `cash` → no URL; `bold` → reuses `BoldService.createPaymentLink` with reference `ORDER-<saleId>-<base36 timestamp>` and the optional `CUSTOMER_PAYMENT_RETURN_URL` callback; `addi`/`sistecrédito` → **stubs** (`PaymentsService.createFinancingLink`) that log the payload (never the API key) and return a sandbox URL until the real contracts are confirmed (TODO markers in code). Settlement uses `SalesService.registerGatewayPayment(saleId, paidBy, amount?)`: global `tec_sales.id` lookup (`id` is a global PK), idempotent when already paid, inserts `tec_payments` (`CC` for Bold, `ADI`/`Sistecredito` for financing) and credits points with the same due→paid/partial rule; staff `addPayment` now shares the extracted `applyPaymentToSale`. The Bold webhook (`POST /api/webhooks/bold`, same signature verification) branches on `ORDER-` references (`SALE_APPROVED` only) before the billing flow. Financing webhooks `POST /api/webhooks/addi` and `POST /api/webhooks/sistecredito` accept `{ order_id | reference | merchant_order_id, status: approved|paid|completed, amount? }`, require `x-webhook-secret` when `ADDI_WEBHOOK_SECRET`/`SISTECREDITO_WEBHOOK_SECRET` are set, and otherwise warn + run in sandbox mode. **`tec_sales.payment_method`** (v0.3.61, approved DDL `docs/migrations/v0.3.61-add-payment-method-to-sales.sql`) persists the method chosen at customer checkout (`cash|bold|addi|sistecredito`; POS-created sales store NULL). **Run v0.3.61 BEFORE deploying the API build that references it** (the sale INSERT includes the column). Customer order list/detail return `payment_method` so the app can show "Pendiente de aprobación (Addi/Sistecrédito)" before the webhook settles; once settled the effective method comes from `tec_payments.paid_by`. Env: `ADDI_API_KEY`, `ADDI_WEBHOOK_SECRET`, `ADDI_CHECKOUT_BASE_URL` (optional), `SISTECREDITO_API_KEY`, `SISTECREDITO_WEBHOOK_SECRET`, `SISTECREDITO_CHECKOUT_BASE_URL` (optional), `CUSTOMER_PAYMENT_RETURN_URL` (optional); Bold reuses the existing `BOLD_*` vars.
- Product reviews (v0.3.65, approved DDL `docs/migrations/v0.3.65-product-reviews.sql`, `api/src/reviews/`): new `product_reviews` table (`id serial`, `product_id int FK → tec_products ON DELETE CASCADE`, `customer_id int FK → tec_customers ON DELETE SET NULL`, `rating int 1..5`, `comment text`, `created_at`/`updated_at`). **No `tenant_id`** — every operation first validates the product belongs to the customer's tenant via `tec_products`. Endpoints (all `JwtAuthGuard` + `CustomerContextGuard`): `GET /api/customer/reviews/:productId` (newest first, max 100, joins `tec_customers.name` as `customer_name`), `GET /api/customer/reviews/product/:productId/average` (`{ product_id, average_rating: number|null, reviews_count }`, average rounded to 2 decimals, `null` when no reviews), `POST /api/customer/reviews` (`{ product_id, rating 1..5, comment? ≤500 chars }`, trimmed; empty comment stored as NULL). **One review per customer per product is enforced twice**: a DB `UNIQUE (product_id, customer_id)` constraint (`unique_product_customer_review`, guarded in the migration so it is re-runnable) plus a service pre-check that returns `400 "Ya calificaste este producto"` (the service also maps unique-violation `23505` from the INSERT to the same 400, covering races). The table is probed with `to_regclass` (60 s cache): GETs return `[]`/null-average when missing and POST returns 503 with the migration hint, so the API can deploy before the migration. The customer product list (`withRatings` flag, only passed by `/api/customer/products`) enriches products with `average_rating` (2 decimals, null without reviews) and `reviews_count` via one grouped `= ANY($1::int[])` query; POS catalog is unaffected. The product projection also gained resolved `image_2_url`/`image_3_url` (same `image_url` resolution) for the app's 3-image gallery.
- Customer addresses (v0.3.69, approved DDL `docs/migrations/v0.3.69-customer-addresses.sql`, `api/src/addresses/`): `customer_addresses` (id serial, `customer_id` FK → tec_customers ON DELETE CASCADE, `label` in `Casa|Trabajo|Otro`, `street_address`, `neighborhood`, `city` default 'Bogotá', `phone`, `additional_notes`, `is_default`, timestamps; index on `customer_id`). Endpoints (`JwtAuthGuard` + `CustomerContextGuard`, customer from the token): `GET /api/customer/addresses` (default first, then oldest), `POST /api/customer/addresses`, `PUT /api/customer/addresses/:id`, `DELETE /api/customer/addresses/:id`, `PUT /api/customer/addresses/:id/set-default`. Invariants: the first address is forced default; `is_default: true` unsets the others in the same transaction; `is_default: false` on update is ignored (mark another address instead); deleting the default promotes the oldest remaining. Phone is stored digits-only; optional text is trimmed ('' → NULL; empty city → 'Bogotá'). Fail-safe `to_regclass` probe (60 s cache): GET returns `[]` and writes return 503 with the migration hint when the table is missing.
- Customer payment methods (Option A, no DDL, `api/src/payments/payment-methods.controller.ts`): `GET /api/customer/payment-methods` derives the methods the customer actually used from `tec_payments` joined to their `tec_sales` (`{ method: paid_by, last_used_at, times_used }`, newest first). **No card data is stored** (no PCI scope); the Flutter screen maps the raw `paid_by` values to labels/icons and shows them read-only.
- Customer combos (v0.3.76, approved DDL `docs/migrations/v0.3.76-add-combos.sql`, `api/src/combos/`): `tec_combos` (per-tenant `name`, `description`, `combo_price`, `original_price`, `is_active`) plus **`tec_customer_combo_items`** for the app's combo components (`combo_id`, `product_id`, `quantity`). ⚠️ The legacy PHP POS table `public.tec_combo_items` **already exists with a different structure** (`product_id` = combo product, `item_code`, decimal `quantity`); never create/reuse it — the app items live in `tec_customer_combo_items` because `CREATE TABLE IF NOT EXISTS tec_combo_items` would silently no-op. `GET /api/customer/combos` (`JwtAuthGuard` + `CustomerContextGuard`) returns active combos with resolved component names/images, `[]` when the tables are missing (`to_regclass` probe, 60 s cache). Both customer checkouts accept `{ items?, combos?: [{ combo_id, quantity }] }` with `items` now optional (combo-only orders); `SalesService.createSale` expands each combo into its component sale lines at **current component prices** (stock deducted normally, points earned per component), and the saving (`components subtotal+tax − combo_price`, clamped ≥ 0) is injected as a fixed `order_discount`/`order_discount_id`; there is **no per-sale combo traceability yet** (would need new DDL). Combos are **cash/contraentrega or Bold (tarjetas/PSE) only**: `POST /api/customer/checkout-with-payment` allows `cash` and `bold` with combos and rejects `addi`/`sistecredito` (400, "Los combos solo están disponibles para pago en efectivo/contraentrega o tarjetas/PSE."), while plain `POST /api/customer/checkout` creates a `due` order whose staff settlement is not combo-restricted. Checkout with combos returns 503 with the migration hint when the tables are missing; combos without configured products, unknown/inactive combos and invalid quantities return 400/404. Empty `items` are allowed only when combos are present (`La venta no tiene productos` otherwise).
- Rewards redemption (P13, v0.3.72, DDL `docs/migrations/v0.3.72-add-points-cost-to-products.sql`): `tec_products.points_cost` (integer, default 0, CHECK >= 0) marks redeemable products; `listRewardProducts` filters `points_cost > 0` (not `reward_points`) and `listProducts` returns it. `POST /api/customer/redeem` (`JwtAuthGuard + CustomerContextGuard`) is atomic: product `FOR UPDATE` in tenant (`points_cost > 0`, `quantity > 0` else "Sin existencias"), customer `FOR UPDATE` (balance >= cost else "Saldo de puntos insuficiente"), deduct points, `quantity - 1`, insert a $0 sale (`payment_method='points'`, `status='due'`, `created_by=NULL`, `store_id=NULL`, `total_reward_points=0`) plus its `tec_sale_items` line, a **60 s in-memory duplicate guard** per customer+product and `customer_points_redeemed` activity (best-effort). Web POS: the product modal has "Costo en Puntos (Canje)" and Pedidos App renders "Canje de Puntos" instead of $0. Flutter (tienda_virtual): `Product.pointsCost`, redeem button in rewards/product detail with confirmation, disabled "Te faltan X puntos", and refresh of profile+orders after success.
- App management (P14, `api/src/app-management/`, admin-only via `AdminGuard`): `GET /api/admin/app-orders` lists sales with **`created_by IS NULL`** (mobile app origin; `payment_method` comes from `tec_sales`) and `PATCH /api/admin/app-orders/:id/delivery` updates `status_delivery` (empty string clears it, only for app orders). `GET /api/admin/app-customers` lists `tec_customers` with `password IS NOT NULL` (+`points_balance`, search by name/email/phone). `PATCH /api/admin/customers/:id/points` adjusts the balance inside a transaction (`FOR UPDATE`, result never negative) and logs with `Logger` + `tec_tenant_activity_logs` best-effort (`customer_points_adjusted`). `POST /api/admin/customers/:id/reset-password` sets `password = NULL` and clears `tec_login_attempts` for the customer's email (lowercase) and phone (digits) identities. `GET/DELETE /api/admin/reviews/:id` lists `product_reviews` scoped through `tec_products.tenant_id` (product/customer names joined) and deletes rows hard. `GET/POST/DELETE /api/admin/banners(/:id)` manages the **global** `banners` table (bigint id, only `image_url`/`created_at`; it is NOT tenant-scoped, so any tenant admin manages the app-wide carousel). Web: `/tienda-virtual` (`AdminOnly`) with tabs Pedidos App / Clientes App / Reseñas / Banners and the sidebar item 📱.
- Global dashboard (`GET /api/dashboard/global`, super-admin only via `SuperAdminGuard`, linked from the global view): **business metrics only, never tenant POS sales**. Returns active subscriptions total + by plan, plans sold today (completed `tec_tenant_payments` with `payment_date = today`), monthly revenue + MRR (yearly/12 over active subs), pending payments and overdue subscriptions (active/suspended/expired with `COALESCE(next_billing_date, subscription_end_date) < today`, amount = plan price by cycle), new subscriptions/plan changes (with `upgrades`/`downgrades` counts) / cancellations this month, trials (active / expiring in 7 days / converted), the last 8 completed subscription payments and the last 6 `plan_changed` events with tenant, `from → to` and `direction`. Day and month boundaries use the business timezone (`POS_TIMEZONE`); if the v0.3.11 tables are missing it returns 503 with the migration hint.
- Tenant management platform (v0.3.11, `api/src/tenant-management/`): all endpoints are super-admin only. The API probes the four approved tables at startup; while they are missing it logs a warning and returns 503 from these endpoints (the rest of the POS keeps working), so **run `docs/migrations/v0.3.11-tenant-management.sql` before deploying and restart the API after it**. `performed_by` is INTEGER (`tec_users.id` is an integer identity, not uuid). New tenants start in a 14-day trial (a paid `plan_id` at creation starts active monthly with end/next-billing +1 month); `refreshLifecycleStatuses()` runs at startup and every 6 h (trial → expired when `trial_end_date < today` and no `subscription_start_date`; active → expired when `auto_renew = false` and `subscription_end_date < today`). A generic `PATCH /tenants/:id/subscription` changes plan/billing_cycle/auto_renew (plan must be active; creates the subscription lazily) and logs `plan_changed` with `from`/`to` names and ids plus `direction` (`upgrade`/`downgrade`/`change`, comparing the normalized monthly price: `price_monthly`, else `price_yearly`/12). Suspend (`POST .../suspend`, reason required) sets the subscription to `suspended` **and** `tec_tenants.status='inactive'` so login is blocked; reactivate restores both and logs. `POST .../payments/record` inserts `tec_tenant_payments` (completed), activates the subscription and sets `subscription_end_date`/`next_billing_date` (+1 month/year per `billing_cycle`) in one transaction; logging is best-effort and never blocks the operation. Plan limits: `assertCanAddUser` (active users) is enforced in `users.service.create`; `assertCanAddStore` is implemented and ready but no store-creation endpoint exists yet; tenants without a plan fail open. There is no email service, so expiry notifications are out of scope (future enhancement).
- `tec_product_store_qty.quantity` is INTEGER and `price` is REAL; V1 store stock is whole-unit only and money calculations use decimal arithmetic.
- All browser data access goes through the server, never Supabase JS/Data API. Existing RLS/grants remain unchanged and must not be treated as the app's tenant boundary.
- Management endpoints (`/api/products`, `/api/expenses`, `/api/reports`, `/api/users`, `/api/suppliers`, `/api/purchases`) are admin-only via `AdminGuard`; registers (`/api/registers`) are available to staff **per cashier**: non-admin `list`/`current`/`summary` scope by `user_id`/`s.created_by` (no `store_id` required), `open` is per user, and `close` only allows the register owner (or a legacy store-scoped row with no `user_id`); admin/super_admin see the whole tenant and can pass `store_id`. Customers (`/api/customers`) are available to admin **and** staff: `GET` returns global + own-store customers, staff `POST` is forced to their `store_id`, staff `PUT` only works on their own store's customers (cannot move to another store or edit global ones), and there is no delete endpoint. Admin keeps full access. **`super_admin` counts as admin everywhere**: services must use `isAdminRole(group_name)` (`api/src/common/roles.ts`, accepts `admin` and `super_admin`) instead of comparing to `'admin'` (only `users.service` role mapping and last-admin counting intentionally stay `'admin'`-only). `tec_purchases` is schema-verified: use `reference_no` (there is no `reference`) and it has no `store_id`/`received`; `tec_purchase_items` has no `sale_price`/`profit_margin`. Purchase quantities are whole units and update `tec_product_store_qty` (the `store_id` lives there and in the request), plus product cost/price. `PUT /api/purchases/:id` mirrors create inside a transaction: subtract old item stock, apply the new lines, update `reference_no/date/note/total/supplier_id`, keep `created_by`. Since the header has no store, stock corrections use the request `store_id`; the UI must keep the original store. No DDL.
- Business timezone: `TenantTimezoneService` (`api/src/common/tenant-timezone.service.ts`, global via `DatabaseModule`) resolves each tenant's IANA timezone from `tec_tenant_settings.timezone` (60 s cache) and falls back to `POS_TIMEZONE` (default `America/Bogota`). Registers, the sales daily report, the sales-history date filter, and **all** report/calendar/top-products aggregations compare and bucket with `AT TIME ZONE $tz` (never hardcode UTC); purchases/expenses use their pure `DATE` columns. Default dates are computed server-side with `todayInTimeZone(tz)` / `daysAgoInTimeZone(tz, n)` (never `toISOString`). The web sets a module business timezone from `settings.timezone` (`setBusinessTimeZone` in `SessionProvider`) and must use `todayInBusinessTimezone()` / `daysAgoInBusinessTimezone()` (never `new Date().toISOString().slice(0,10)` nor browser-local `getFullYear/getMonth`) so date pickers and the calendar do not shift by a day.
- Sales (`/api/sales`) list/create are available to staff scoped to their own store; `GET /api/sales/:id` returns header + items + payments plus `cashier_name` (resolved from `created_by` → `tec_users` full name, falling back to username) so the history ticket shows the cashier like the POS immediate view (staff only for sales of their `store_id`). `GET /api/sales` accepts `from`/`to` (both required together) and an optional `customer` filter: partial, case-insensitive `ILIKE` on `customer_name` with `%`/`_` escaped, max 100 chars. When `customer` is present the date range is ignored on purpose (search across the whole history); the date branch is only used when there is no customer filter. `PUT /api/sales/:id` and `DELETE /api/sales/:id` are admin-only and mirror the legacy POS inside a transaction: restore the old store stock, replace/adjust items with whole quantities, keep historical unit prices, recompute totals/status from the existing `paid`, and delete `tec_sale_items`/`tec_payments` before `tec_sales`. Reject combo and custom (null `product_id`) lines instead of guessing stock restoration.
- Adding a payment: `POST /api/sales/:id/payments` with `{ amount, paid_by }` (decimal string + allowed method). Allowed for admin and for staff only on sales of their own store. Inside a transaction with `FOR UPDATE`: validate `0 < amount <= grand_total - paid`, insert into `tec_payments` using only existing columns (`tenant_id, sale_id, amount, paid_by, created_at`), then set `tec_sales.paid = paid + amount` and recompute `status` (`paid`/`partial`/`due`). Never add `notes`/`payment_date`/`created_by` to `tec_payments` (no such columns; no DDL). The service logs the action with the user id.
- Never enable `PASSWORD_REHASH_ENABLED` while the legacy sha1 POS shares `tec_users`.
- User management (`/api/users`) is admin-only: creates/edits `tec_users`, resolves the role through `tec_groups` (admin/staff, tenant or global), requires a store for staff and soft-deletes via `active`. New passwords use `USER_PASSWORD_METHOD` (default `sha1` for legacy compatibility; `bcrypt` only after cutover). Never return password hashes; never allow deactivating one's own account or the last active admin.
- Product images come from `tec_products.image`/`image_2`/`image_3`; full URLs (Supabase Storage) are returned unchanged, legacy filenames fall back to `PRODUCT_IMAGE_BASE_URL` (default `/uploads/thumbs`, mounted read-only via `LEGACY_UPLOADS_PATH`). Never rewrite absolute image URLs. Image uploads/deletes go through the API with the service role into `SUPABASE_PRODUCT_BUCKET` (default `productos`, max 2 MB, JPG/PNG/WEBP) and store URLs built from `SUPABASE_PUBLIC_URL`, which is required and must be a browser-reachable host (never `supabase-kong` or another internal name); the browser never talks to Supabase Storage directly.

Commands from this directory: `npm install`, `npm run dev:api`, `npm run dev:web`, `npm test`; build/push with `docker compose -f docker-compose.build.yml build --pull` and `docker compose -f docker-compose.build.yml push`; deploy pulled images with `docker compose pull` and `docker compose up -d`.
